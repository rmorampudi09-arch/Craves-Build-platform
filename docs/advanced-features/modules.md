# Advanced features — module notes and decisions

All routes are under `https://api.craves.in/api/v1/advanced/` behind one gateway API with wildcard operations, so later modules ship without any gateway change. Contracts: `contracts/openapi/advanced/` (`x-craves-auth`: public, user or staff).

Decisions made while building (the owner asked for no questions; each choice is the conservative one and easy to change).

## M01 Food lists (E04, E40)
- Lists are private. Sharing creates one link per list (`/l/<token>` on craves.in); the token is shown once and stored only as SHA-256. Rotating revokes the old link; revoking ends access at once. Optional expiry 1–365 days.
- A shared view shows list name, description and dishes with live availability. It never shows the owner, their other lists, addresses or orders. Anyone signed in can copy a shared list into their own lists.
- Limits: 50 lists per person, 200 dishes per list. Dish names are snapshotted so unavailable dishes stay understandable.

## M02 Group orders (E13)
- One kitchen per group (multi-chef economics is a product decision), host pays (split payments deferred by the handbook).
- Join with an 8-character code (`XXXX-XXXX`, 40 bits) inside a join window (15 min–24 h, default 60). After the window the group locks itself.
- Each person edits only their own dishes; the host can remove people, lock/unlock, cancel and hand off. Up to 20 people, 20 dishes each, 100 of one dish per order.
- Checkout hand-off re-reads live prices and refuses if any dish became unavailable. With `applyToCart=true` it fills the host's real cart through Order service (refuses a non-empty cart unless `replaceCart=true`); Order service stays the authority for the final total. Repeating the hand-off returns the stored result.
- Closed groups are purged after 30 days, abandoned ones 7 days after their window.

## M03 Food facts (E19)
- Chefs declare ingredients, allergens (FSSAI 2020 list plus common extras), "may contain", nutrition per serving and the source (chef-declared, lab-tested, label-derived). Ownership is confirmed with Catalog using the chef's own token.
- Submitting publishes the facts at once labelled CHEF_DECLARED (the newest recipe is the safest truth for allergens); staff verification relabels them VERIFIED. A rejection falls back to the last verified facts, or removes them.
- Plausibility checks (energy vs macronutrients, sugars vs carbohydrate, saturated vs total fat, nutrients vs serving size, missing evidence) are warnings, never blocks.
- "Free from" search only returns dishes whose facts were declared: unknown is never treated as safe. Every public answer carries a plain disclaimer.

## M04 Cuisine and diet taxonomy (E10)
- The vocabulary is data, not code. A baseline is seeded (7 top-level groups — five Indian regions, Indo-Chinese, Continental — and 23 regional cuisines up to three levels deep, e.g. South Indian → Karnataka → Udupi, and 6 diets: Jain, no onion/no garlic, Satvik, Vegan, Fasting (vrat), Halal); platform, chef and compliance admins add, rename, move and retire terms. Terms are never deleted and codes never change, so dish labels stay valid; retired terms drop out of every public answer.
- Diets here are eating practices only. Allergen claims (gluten-, dairy-, nut-free) stay with food facts (M03), veg/non-veg/egg with Catalog `foodType`, spice with Catalog `spiceLevel`. No health claims (diabetic-friendly, keto) without an owner decision.
- Chefs label their own dishes (ownership confirmed with Catalog using the chef's token): 1–3 cuisines (the first is the main one) and up to 6 diets, published at once as `declaredBy: CHEF`. Staff can correct a dish's labels with a reason (`declaredBy: STAFF`, audited with before/after). The chef can change them again (also audited); repeated false claims are a trust case for M12.
- Browse: a region matches every cuisine below it (retired ones too, so a dish stays South Indian), diets are all-of, and dishes without labels never match. Answers are menu-item ids; Catalog stays the authority for availability and price.
- `resolve` maps free text (for example the cuisine words kitchens typed into Catalog) to terms by code, name or alias, ignoring case, punctuation and spacing in any script. An alias belongs to at most one live term, so the answer is never ambiguous.
- No personal data. Customer diet preferences belong to taste memory (M06) / personalised ranking (M18), behind PersonalDataContributor.

## M05 Menu options and meal hours (E16)
- Each dish can have up to 10 option groups (for example "Rice": choose exactly 1, "Add-ons": choose up to 2), each with up to 20 choices. Choice prices are set by the chef in paise and are never negative (model "Half/Full" as a base price plus a Full add-on); a choice can be switched off for the day (`available: false`). Group and choice ids stay the same across edits when the chef app sends them back, so carts can hold them.
- The dish's base price always comes live from Catalog. `POST /quote` (signed in) checks Catalog availability, the picks against every group's minimum and maximum, availability of each pick and the meal hours, and returns unit and total price in paise. It stores nothing; checkout use waits for M24 (order-service hook, flag default off). The quote's `at` comes from the client, so the meal-hours answer is advisory: M24 must check meal hours against the order's real time.
- Meal hours: each chef sets their kitchen's windows (Breakfast, Lunch, Snacks, Dinner, Late night) in India time, with days of the week; a window may run past midnight. A dish labelled with meals is quotable only inside those windows; a dish without meal labels follows the kitchen's normal opening hours (Catalog schedule). A meal cannot be labelled before its hours exist, and hours cannot be removed while dishes use them.
- The chef's kitchen is taken from their own Catalog menu (Catalog has no other chef-to-kitchen read here), so a chef adds a dish before setting meal hours.
- No personal data. Remembering a customer's usual picks is taste memory (M06).

## M06 Taste memory (E03)
- A signed-in person keeps a taste profile (spice: mild/medium/spicy, the same words as Catalog's dish spice level; oil: less/regular; a short note for the chef such as "less salt") and, per dish, the option choices they picked last time (M05 choice ids) with their own spice, oil and note.
- Only what the person asks to remember is stored (the apps' "Remember my choices"); nothing is inferred from orders, so it does not depend on the personalization consent. Inferring tastes from orders would be personalization (M18) and must read that consent.
- Remembered choice ids are hints: the apps preselect only choices the dish still offers, and M05's quote stays the check at order time. Up to 500 dishes per person; the list is newest first.
- Personal data: exported and erased by `my-taste-data` (PersonalDataContributor). No one else, staff included, has a route to it.

## M07 Small batches and kitchen load (E05, E20)
- A chef publishes a batch of a dish for an India date (today up to 30 days ahead): portions (1–1000), an optional order cutoff and an optional ready time. The chef can change portions (never below what is already held or confirmed), the cutoff and the ready time, or close the batch; holds already taken stay valid.
- A signed-in person holds portions while checking out (one live hold per person per batch; at most 50 portions per person per batch, held and confirmed together; `Idempotency-Key` supported), then confirms the hold with the order id it became, or releases it. Holds are accepted only while the batch is open, before its cutoff and before its India service date is over. A hold lasts 10 minutes (`CRAVES_ADV_BATCH_HOLD_MINUTES`, kept between 1 and 60; an unreadable value means 10); expired holds simply stop counting (30 seconds later, so replicas with slightly different clocks never sell a portion twice), so nothing needs sweeping. Holds, confirmations and voids lock the batch row, so portions are never sold twice.
- Confirmation stores the order id as given: order-service is not asked yet. The chef therefore sees the batch's live and confirmed holds (without who holds them) and can void any that no real order backs; voids are audited with the reason. Moving hold and confirm into checkout (and releasing on order cancellation) is M24, behind its flag; until then the per-person cap and chef voids bound abuse, and M12 (trust) covers repeat offenders.
- Kitchen-wide capacity and preparation time from live order counts need order-service data, so they are part of M24. Here the chef sets their own "busy" extra preparation time (0–180 minutes, for up to 24 hours), shown on top of each dish's usual preparation time.
- Holds are personal data: my-taste-data exports them; erasing deletes released or expired holds and unlinks the rest from the person (the portions stay counted, so the batch stays right).

## M08 Promotions and coupons (E23)
- Staff enter every commercial value; nothing is seeded or defaulted: percent off (1–100, optional cap) or a flat amount in paise, minimum order, kitchens (none = every kitchen), who funds it (Craves or the kitchen; a kitchen-funded promotion must name its kitchens), per-person limit (1–100), total budget (required, so no promotion can run without a ceiling), optional redemption cap, start and end. Platform and payments admins edit; support and audit admins read. Every change is audited.
- A promotion is created as DRAFT and goes ACTIVE ⇄ PAUSED → ENDED (ENDED is final). Once it has been active its terms (code, discount, cap, minimum order, kitchens, funding, per-person limit, start) are frozen, so no customer is promised one thing and given another; name, title, description, listing, end time, budget and redemption cap can still change, but never below what is already reserved or used.
- With a code (letters and digits, 4–20, case-insensitive, never reused) a promotion applies only when typed; without one it applies by itself, and the quote picks the largest discount among those that fit the cart (ties: the one ending soonest). `listed` decides whether `GET /offers` shows it; offers never show budget or usage. A draft's code answers like an unknown code, so codes cannot be discovered before launch. One promotion per order: promotions never stack, enforced by a unique confirmed order id.
- The cart is priced with the dishes' live Catalog prices (base price × quantity; option add-ons are not counted, so the discount and the minimum-order check can only err low). Only dishes from the promotion's kitchens count. Discounts round down to whole paise and never exceed that part of the cart. Order-service stays the authority for the final total.
- Checkout flow for M24: reserve (signed in, `Idempotency-Key` supported; budget, redemption cap and per-person limit are checked and taken under a row lock, so a budget is never overspent), then confirm with the order id, or release. A reservation lasts 10 minutes (`CRAVES_ADV_PROMO_RESERVATION_MINUTES`, kept between 1 and 60; unreadable means 10) and keeps counting 30 seconds after it expires (replica clock skew). As in M07, confirmation stores the order id as given until M24 moves reserve/confirm into checkout (and release into order cancellation); until then the per-person limit, the budget and staff voids (audited, with a reason) bound abuse. M24 must also check that the order belongs to the person and recompute the discount from the real order. Pausing or ending a promotion never depends on Catalog (only kitchens newly added to a draft are checked), so staff can always stop one.
- Not decided here (owner decisions, left out on purpose): stacking with the referral invitee discount (M24 must not combine them unless the owner says so), first-order-only offers (need order history: M24), dish-level offers, and chef self-service promotions (kitchen-funded discounts change settlements, E34).
- Redemptions are personal data: my-taste-data exports them; erasing deletes those that no longer count and unlinks the rest from the person (the discount stays counted against the budget). Erasing therefore also clears that person's per-person count; M24 should enforce per-person limits from order-service's own order history.

## M09 Party and bulk orders (E14)
- The rules are staff data with no defaults: minimum portions, minimum notice in hours, how many days ahead, and the deposit share of a quote (0–100 %). Until platform or payments admins set them, requests answer `503 BULK_ORDERS_NOT_CONFIGURED`; rules whose minimum notice exceeds the booking horizon are refused. Each change is a new, audited version; `GET /policy` is public so the apps can show the rules.
- A signed-in customer asks one kitchen for its dishes (up to 30, quantities summed per dish), for an event time that fits the rules, with optional guest count and notes for the chef. Dishes must be on that kitchen's menu as Catalog shows it publicly today (a dish the chef switched off for today can be asked for once it is back on; a Catalog read of active-but-unavailable dishes would lift this). At most 5000 portions of one dish. Names and list prices are snapshotted. At most 10 open requests per person whose events are still ahead, so chefs cannot be flooded (checked before Catalog is asked; the check is not atomic, so requests sent at the same moment can each pass it).
- The kitchen's chef (ownership through Catalog with the chef's token; another kitchen's request answers like a missing one) quotes a price per requested dish (at most 1,00,000.00 a portion, a bound against typos and overflow, not a price rule), every dish exactly once, with a validity that ends no later than the event; a new quote replaces the last one and is audited. The deposit is the current staff-set share of the total, rounded down to whole paise, and is fixed into the quote. The chef can decline with a reason (audited).
- The customer accepts the quote they saw (`expectedVersion`) while it is valid and before the event, or cancels while it is open. An accepted request is final here: placing the order and taking the deposit is M24 (order-service), and cancelling it after acceptance follows the order's cancellation and refund rules (M23), not this module. Requests lapse (`expired: true`) when the event passes, quotes when their validity passes; the chef may quote again until the event.
- The chef never sees who asked (no customer id in any view); contact happens through the order or support chat. Requests are personal data: my-taste-data exports them; erasing deletes them, except accepted ones still to be cooked, which are unlinked from the person and lose their notes.
- Not built (no owner decision yet): staff browsing of requests, negotiation threads, delivery addresses (they belong to the order), and multi-kitchen requests.

## M10 Corporate and team meals (E15)
- Craves staff (platform and payments admins; support and audit admins read) create each company with a seat limit and enter its terms as agreed with the company; nothing is seeded or defaulted, so a company pays for nothing until its terms are set (`409 COMPANY_TERMS_NOT_SET`). Terms: the share of a meal the company pays (1–100 %) up to a per-meal maximum, meals per member per India day (1–5), meal days and one daily window in India time (it cannot run past midnight), a monthly budget per India month (required, so no company runs without a ceiling), an optional monthly cap per member, and payment terms in days (the statement's due date). New terms apply from the next reservation; confirmed charges keep their amounts. Every change is audited; suspending a company stops new and pending charges at once.
- People: one company per person at a time. Staff add a person with a role (`MANAGER` runs invites, members and statements; `MEMBER` orders). Managers create invite codes (43 random characters, shown once, stored as SHA-256; 1–30 days, a use limit no larger than the seat limit, at most 20 open per company) and can revoke them or remove members; managers themselves are changed by staff. A person joins with a code and the name their company sees (at most the seat limit; joining the same company again is harmless) and can leave at any time.
- The share: whole paise, rounded down, never more than the meal or the per-meal maximum, and trimmed to what is left of the company's monthly budget and of the member's monthly cap; when nothing is left the request is refused with the reason. The meal counts on the India date and time it is charged (the order's time, not the delivery time). The cart is priced with live Catalog prices (base price × quantity; option add-ons are not counted, so the share can only err low); order-service stays the authority for the total.
- Team meals: a manager orders for a team (`kind: TEAM_MEAL`, headcount 2 up to the seat limit, same days and window); the company pays its share up to the per-meal maximum times the headcount. Team meals count only against the company's budget, never against the manager's own meals or cap. Collecting each person's picks is M02 group orders (host = the manager); the company payment applies at that group's checkout.
- Checkout flow for M24 (same as M08): reserve (signed in, `Idempotency-Key` supported; one waiting reservation per person; budget, daily meals and the member cap are checked and taken under the company's row lock), then confirm with the order id, or release. A reservation lasts 10 minutes and keeps counting 30 seconds after it expires (replica clock skew). Confirmation needs the person still to be a member of an active company and stores the order id as given until M24 moves reserve/confirm into checkout (and release into order cancellation); one company payment per order (unique confirmed order id). Staff can void a charge (audited, with a reason), which gives it back to the budget.
- Statement per India month (staff and the company's managers): confirmed charges only, totals and one line per person (meals, team meals, company share), and the due date (from the company's current payment terms; an invoice made from a statement keeps its own). Invoices and GST documents are not built here (E35 documents, finance): the statement is their data.
- Personal data: membership, charges (with the names they carry) and the invites a manager created are exported by my-taste-data; erasing ends the membership, deletes charges that no longer count, unlinks the rest and the invites from the person (the amounts stay on the company's statement), and waits for a reservation being made at that moment. Erasing and rejoining therefore resets that person's daily meals and monthly cap here (each rejoin needs an invite with uses left, and the company budget still caps the total): M24 should enforce per-member limits from order-service's own order history, as for M08. Names that are blank after trimming (for example only Unicode spaces) are refused.
- Not built (no owner decision yet): company self-service sign-up, cards or wallets on file and how the company actually pays Craves (credit, prepaid), per-kitchen or per-dish restrictions, night-shift windows past midnight, more than one window a day, and company-wide delivery addresses.

## M11 Order amendments and substitutions (E17)
- A change to a placed order needs both sides: the customer asks and the kitchen's chef accepts or declines, or the chef proposes (for example a substitution when an ingredient ran out) and the customer accepts or declines. The proposer can withdraw while it waits. Order service is read with the caller's own token (customer `GET /api/v1/orders/{id}`, chef `GET /api/v1/chef/orders/{id}`), so each side only ever reaches its own orders; another kitchen's order or proposal answers like a missing one.
- When: the customer may ask while the order is `PAID`, `CHEF_ACCEPTANCE_PENDING` or `CHEF_ACCEPTED`; the chef may propose from `CHEF_ACCEPTANCE_PENDING` to `PREPARING`; a proposal can be accepted only while the order is still in the kitchen (`PAID` to `PREPARING`) and before it lapses. Order service does not record `PREPARING` today (an accepted order goes straight to `READY_FOR_PICKUP`), so `CHEF_ACCEPTED` also covers cooking and the chef's answer is the real gate; narrowing the customer's window is an owner decision. One proposal waits at a time per order, each side makes at most 5 per order (any outcome, so neither side can use up the other's), and an unanswered one lapses after 10 minutes (`CRAVES_ADV_AMENDMENT_ANSWER_MINUTES`, kept between 1 and 60; unreadable means 10). Accepting needs the version the person saw; repeating an answer is harmless. Once a newer proposal exists, an older one can never be accepted, whatever the answering replica's clock says (the service runs on several replicas).
- What: per order line, REMOVE, REDUCE (to a lower quantity), REPLACE (another dish of the same kitchen that Catalog sells right now), or ADJUST (same dish, changed preparation such as "tofu instead of paneer" or "no onions"; needs a note). Nothing can make an order cost more: a substitute may cost at most what the customer paid for the line, and adding dishes is a new order. Removing every dish is refused (that is a cancellation, with its own rules). Every reason a change does not fit is reported at once.
- Money: changes are priced at the order lines' own prices, before order-wide discounts such as the referral invitee discount, wallet or promotions (and Catalog's price of a substitute at proposal time), and the amendment records the gross food subtotal change, never above zero. Nothing here refunds, charges or edits the order: M24 applies accepted changes in Order service and refunds through the existing refund rules (M23), sharing any order-wide discount across the lines so it never refunds more than was paid, and must then mark them applied (a V2 migration adds that status) so they are not replayed. Until then accepted changes replay over the order's lines in sequence, so a line is never removed or refunded twice.
- No customer id in any view (the chef sees the order, not the person); staff (platform, support, operations, audit admins) read every change on an order for support cases and disputes. The audit trail records what changed and the amount, never the notes.
- Personal data: my-taste-data exports every change the person asked for, proposed or answered; erasing deletes the customer's changes that never took effect, keeps accepted ones with the order (the kitchen needs them) without the person and without any notes, and unlinks a chef from what they proposed or answered. Erasing waits for a proposal being made at that moment, and the order's sequence continues after it.
- Not built (no owner decision yet): pricier substitutes with an extra payment, adding dishes to a paid order, push notifications to the other side (the apps read `GET /chef/pending` and the order's list), and automatic outcomes when nobody answers (a lapsed proposal changes nothing).

## M12 Trust: reports, disputes and risk flags (E29)
- Reports (moderation): any signed-in person reports a kitchen, a dish, a review or a person, with a reason (food safety, hygiene, wrong label, misleading, abuse, fraud, spam, other), their own words and optionally the order it concerns. One open report per person and target, at most 20 a day per person. Targets are not checked against other services, so a dish switched off today can still be reported; staff triage. Platform, compliance and operations admins uphold or dismiss with a note (audited without the reporter's words); acting on an upheld report (removing a review, pausing a kitchen, correcting a label with M04's staff correction) is done where that content lives. The reporter sees the outcome, never staff notes or who decided.
- Disputes: the customer disputes their own paid order (read from Order service with their token) once it is over (`DELIVERED`, `CHEF_REJECTED`, `REFUND_PENDING`, `REFUNDED`, `REFUND_FAILED`; not `CANCELLED`, which Order service sets only before payment) and within the staff-set window counted from the order's last change (about when it finished, so a scheduled order delivered days after checkout keeps its window). The window has no default: until platform or payments admins set it (each change a new audited version; `GET /disputes/policy` is public), disputes answer `503 DISPUTES_NOT_CONFIGURED`. Only a delivered order can get money back here (`refundablePaise` = its total); Order service already refunds rejected and refunded orders in full, so their disputes are about the refund itself and can refund nothing more. A claim, when given, is at most `refundablePaise`. One live dispute per order; a withdrawn one may be opened again, at most 3 in all.
- The kitchen's chef sees the disputes about their orders, outcomes included (never who opened them), and adds their side while a dispute is open. Platform and payments admins decide RESOLVED (optionally with a refund, at most `refundablePaise`) or REJECTED, with a note both sides see and the version they saw. Support admins only read (Auth defines the role as read-only). No staff member decides their own case: not a dispute they opened or answered as the chef or about their own kitchen, not a report they filed or that names them, not a flag on themselves. Nothing here pays: Order service pays a decided refund through its refund rules (M24/M23) and must take off wallet and referral discounts, because the order total here is before them.
- Risk flags (fraud risk): platform, compliance, operations and payments admins raise a flag on a person or a kitchen (severity, reason) and clear it with a note; both are audited. The subject summary gives counts only (open flags; reports open, upheld, dismissed; disputes open, resolved, rejected and the refunds decided): what to do at which numbers is a staff decision, so no automatic score, threshold or block is built.
- Personal data: my-taste-data exports what the person filed (reports, disputes) and their chef statements. Erasing deletes their dismissed reports; open and upheld reports stay as safety signals without the person and without the order they named; disputes stay as order records without the person and without their description (an open one is withdrawn), so per-order caps keep counting; a chef is unlinked from their statements. Erasure waits for a filing being made at that moment. Trust records about a person (reports naming them, risk flags) are kept for fraud prevention and are not part of the self-service export or erase: a privacy request for them goes to support. Audit rows keep the actor, as everywhere in the platform.
- Owner decisions left open: because erasure unlinks the person, it also resets their daily report count and the disputes counted in their person summary; keeping a pseudonymous counter that survives erasure, or limiting how often a person can erase, would close that. Also not built: automatic risk scores or blocks, evidence uploads (photos), messaging between the sides, appeals, and notifications.
## M13 Experiments and product analytics (E30)
- Variants come from a per-experiment random salt and the person id (SHA-256), so a person always sees the same variant on every replica and nothing is stored to assign them. Weights are relative integers; 2–5 variants. Only drafts can change; DRAFT → RUNNING → STOPPED, never restarted (create a new key), so nobody moves between variants mid-test. Staff editors: platform and operations admins; audit admins may read. Every change is audited.
- `GET /experiments/mine?keys=` works for every signed-in person without consent because it stores nothing; a stopped, draft or unknown key answers `variant: null` (the app shows its default). Anonymous visitors are not assigned (no device-id scheme yet).
- Events are kept only when the person turned on M22 `productAnalytics` (default off); otherwise the batch answers 202 with `recorded: 0` and is dropped unread. The variant is worked out on the server, never taken from the app. Events carry a client `eventId` so retries count once, must be from the last 7 days (5 minutes of clock skew allowed), and have at most 10 flat properties (text up to 100 characters, numbers, true/false). An event naming a draft or unknown experiment is kept without the experiment. The app should send `experiment.exposure` when it shows a variant; results count a person in a variant once they sent any event under it.
- Staff see aggregates only (per-variant people/people-with-event/events, daily counts per India day, up to 92 days); any count below 5 is returned as null so no small group can be singled out. No endpoint returns one person's events except their own export.
- Withdrawing consent stops new events; events already kept stay until the person erases their data (export/erase cover them). No retention period is set: how long analytics events are kept is an owner decision (a purge job is easy to add once a period is chosen).

## M22 Private taste data (E40)
- `GET /api/v1/advanced/my-taste-data/export` returns everything the advanced modules hold about the caller; `DELETE /api/v1/advanced/my-taste-data` with `X-Confirm-Erase: ERASE` erases it and keeps only a receipt (count and modules, no content).
- Consent switches (`personalization`, `productAnalytics`) default to off; later modules (personalized ranking, product analytics) must read them.
- Erasing also deletes the stored replies of the person's keyed requests (`Idempotency-Key`, otherwise kept up to 48 hours); they are caches, so the receipt does not count them.
