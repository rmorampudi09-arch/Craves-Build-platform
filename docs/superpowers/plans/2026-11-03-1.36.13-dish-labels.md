# 1.36.13 Cuisine and diet labels Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Chefs label each dish with up to 3 cuisines and up to 6 diets; customers filter Home by those labels in Filter & Sort, and nothing shows until labelled dishes are nearby.

**Architecture:** A shared availability gate reads `GET /api/v1/advanced/features` once per app session. A new `features/dishLabels` folder holds the taxonomy API client, pure matching rules and a small cache of tags for the dishes on Home. The chef dish form gets a labels section saved through the taxonomy chef route. Filter & Sort (Home origin only) replaces its "coming soon" card with chips built from the tags of nearby dishes, and Home filters by them.

**Tech Stack:** React Native 0.8x, TypeScript, axios clients `apiClient` / `publicApiClient`, Redux Toolkit slice `discoveryFilters`, react-hook-form, Jest + React Native Testing Library.

**Spec:** `docs/superpowers/specs/2026-11-02-advanced-features-app-design.md` (sections "Shared decisions" and "1.36.13"). This is plan 1 of 8; the next plans (1.36.14 … 1.36.20) are written after this version is checked on the phone, reusing the gate from Task 1.

## Global Constraints

- Work only in `C:\madv` (branch `feat/advanced-features-app`), app code under `apps/mobile`. Never touch rider flavor code.
- Advanced routes live under `/api/v1/advanced/`. Authenticated calls use `apiClient` from `src/core/http/apiClient.ts`; public calls use `publicApiClient` from `src/core/http/transport.ts`.
- A feature renders only when `GET /api/v1/advanced/features` lists its id with `enabled: true` and `available: true`; if that call fails, every advanced feature is off for the session.
- Any failing advanced read hides its section silently; actions the user started show the screen's usual inline error.
- No new libraries.
- Parse every response strictly (pattern of `src/features/reviews/api/publicKitchenReviewsApi.ts`): unknown shape → throw `Error('<NAME>_INVALID_RESPONSE')`.
- Taxonomy request rules (contract `taxonomy-v1.yaml`): term codes match `[a-z][a-z0-9-]{1,39}`; at most 3 cuisines (the first is the main one); at most 6 diets; lookup takes at most 100 menu-item ids.
- Filter & Sort opened from the Chefs tab (`origin: 'CHEFS'`) stays exactly as it is today.
- Version: `versionCode 113`, `versionName "1.36.13"`; `CUSTOMER_APP_VERSION` and `CHEF_APP_VERSION` = `'1.36.13'`.
- Test on the owner's chef kitchen "Relangi mavayya kitchen", dish "Ravi's test"; remove the test labels after the phone check.
- Commit only in `C:\madv`; never push without the owner saying so.

## Review Focus

- **More than 100 dishes near the customer:** the tag lookup must split into calls of at most 100 ids and merge the results. Covered in Task 4.
- **Tag lookup fails or is slow while a cuisine/diet is selected:** Home must show its normal, unfiltered results (never an empty "no dishes" screen), and Filter & Sort hides the label sections. Covered in Task 6.
- **A dish tagged with a code that is missing from the vocabulary (retired or new):** ignore that code for chips, but still match it when the customer picked exactly that code. Covered in Task 3.
- **A chef saves labels that someone else changed meanwhile (409/412 on `If-Match`):** show "These labels changed somewhere else. We loaded the latest; check them and save again." and reload; never drop the dish's other changes. Covered in Task 5.
- **A new dish is created but its label save fails:** the dish stays saved and the chef sees "<name> is live, but its labels didn't save. Open the dish to add them again." Covered in Task 5.

### Task 3: Label matching rules

**Files:**
- Create: `apps/mobile/src/features/dishLabels/domain/dishLabels.ts`
- Test: `apps/mobile/src/features/dishLabels/domain/dishLabels.test.ts`

**Interfaces:**
- Consumes: `TaxonomyVocabulary`, `TaxonomyTerm`, `DishLabelCodes` (Task 2)
- Produces:
  - `interface LabelSelection { cuisines: string[]; diets: string[] }`
  - `cuisineLineage(code: string, vocabulary: TaxonomyVocabulary): string[]` – the code then each parent up to the top; stops on unknown parent or a loop
  - `dishMatchesLabels(dish: DishLabelCodes, selection: LabelSelection, vocabulary: TaxonomyVocabulary): boolean` – cuisines: any selected code equals one of the dish's codes or is in its lineage (empty selection = match); diets: every selected diet is on the dish
  - `termsOnDishes(dishes: readonly DishLabelCodes[], vocabulary: TaxonomyVocabulary): {cuisines: TaxonomyTerm[]; diets: TaxonomyTerm[]}` – cuisines present on any dish plus all their known ancestors, in vocabulary order; diets present on any dish, in vocabulary order; codes not in the vocabulary are left out
  - `toggleCuisine(current: string[], code: string): string[]` – removes if present; adds at the end if fewer than 3; otherwise unchanged
  - `toggleDiet(current: string[], code: string): string[]` – same with a limit of 6

- [ ] **Step 1: Write the failing tests** (vocabulary fixture: `south-indian` > `karnataka` > `udupi`, `south-indian` > `andhra`, `north-indian`; diets `jain`, `vegan`)
  - `a region matches dishes from cuisines under it` – dish `{cuisines:['udupi']}`, selection `{cuisines:['south-indian'], diets:[]}` → `true`.
  - `cuisines are any-of` – dish `['andhra']`, selection `['north-indian','andhra']` → `true`.
  - `diets are all-of` – dish diets `['jain']`, selection diets `['jain','vegan']` → `false`.
  - `an unknown code still matches itself` – dish `['new-code']`, selection `['new-code']` → `true`.
  - `terms on dishes include ancestors and skip unknown codes` – dishes `[{cuisines:['udupi','new-code'], diets:['jain']}]` → cuisine codes `['south-indian','karnataka','udupi']`, diet codes `['jain']`.

  - `a fourth cuisine is not added` – `toggleCuisine(['a','b','c'],'d')` → `['a','b','c']`; `toggleCuisine(['a','b'],'a')` → `['b']`.
  - `a seventh diet is not added`.
  - `lineage stops on a loop` – vocabulary where `x.parent = y`, `y.parent = x` → `cuisineLineage('x')` is `['x','y']`.
