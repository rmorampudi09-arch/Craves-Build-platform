# Auth-owned email verification transport

`POST /internal/v1/auth-email/verification` is an Auth-only transport exception to normal verified-recipient email. Never publish it in APIM public APIs/products. Normal notifications always resolve the ACTIVE verified canonical identity address through Auth; `deliveryAddress` cannot override it. The ordinary lookup reuses the existing bounded `DocumentHttp` client (8192-byte cap, total timeout, no redirects); unavailable or mismatched Auth responses never fall back to a supplied address. The existing PDF email gate remains unchanged.

Auth sends JSON `challengeId`, `identityId`, `email`, `code`, and UTC `expiresAt`. The dedicated `CRAVES_EMAIL_VERIFICATION_INTERNAL_KEY` (UTF-8, at least 32 bytes) signs exact raw bytes using HMAC-SHA256 over `POST\n/internal/v1/auth-email/verification\n<epoch seconds>\n<raw JSON>`. Headers are `X-Craves-Email-Timestamp` and `X-Craves-Email-Signature` (hex). Skew is at most 300 seconds. Bodies are limited to 4096 bytes, must contain only the contract fields, and reject duplicate fields/trailing JSON. Response is `{status,challengeId}` with private no-store semantics; status is ACCEPTED, UNKNOWN, or UNAVAILABLE. Unknown outcomes must not be interpreted as failure to deliver.

`CRAVES_EMAIL_VERIFICATION_TRANSPORT_ENABLED` defaults false. This flag is independent of ordinary notification scheduling/channel enablement. Reuse existing ACS connection string, approved sender and reply-to settings. No new provider or resource is created. No Auth browser endpoint can directly choose Notification's ordinary delivery recipient.

V7 adds a dedicated receipt keyed by challenge ID. It contains identity ID, keyed request fingerprint, expiry and outcome only. It stores no OTP, full email address, message body or recoverable payload. The UNKNOWN claim commits before ACS submission. A timeout/crash or duplicate UNKNOWN never resubmits the same challenge. ACCEPTED and FAILED are immutable terminal states; history cannot be deleted. A legitimate Auth resend creates a new challenge under Auth's cooldown/rate limits and invalidates the old code.

ACS uses a dedicated client with 3-second connect and 8-second read/write/response bounds, a 15-second completion wait and zero automatic retries. An eight-call semaphore rejects excess work immediately instead of creating an unbounded transport queue. Once submission starts, exceptions are classified UNKNOWN. OTP stays in transient request/template/SDK memory and is never placed in `notification_request`, logs or analytics. Engagement tracking is disabled.

The responsive white/red HTML and plain text use the exact subject and security warning from the release request. The approved local `DocumentBrand.logo()` checksum is verified and delivered as an inline CID image. No remote image fetch occurs. Azure's existing 1.1.2 SDK supports [inline attachment content IDs](https://learn.microsoft.com/en-us/java/api/com.azure.communication.email.models.emailattachment?view=azure-java-stable).

Required tests: `VerificationEmailSecurityTest`, `VerificationEmailTemplateTest`, `AuthRecipientEmailResolverTest`, and `VerificationEmailReceiptDbTest`. The database suite only permits disposable GitHub CI (`GITHUB_ACTIONS=true`, `EMAIL_TEST_DISPOSABLE=true`, `EMAIL_TEST_DB_URL=jdbc:postgresql://localhost:<port>/craves_email_test`, user/password envs). It exclusively resets `notification_schema`; it must never receive a production URL or production tunnel. CI must assert the required DB cases executed with zero skips.

Production acceptance is separate: authenticated owner requests a real code, confirms branded receipt securely, verifies canonical Auth state and replay/resend behavior, then requests one existing owned PDF email. Mocked transport and disposable DB tests do not prove inbox delivery.
