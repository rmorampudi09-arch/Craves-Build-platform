# Authoritative Auth email projection

Auth is the only email verification authority. A profile email value never establishes verification. V12 is additive and does not backfill or fabricate verification from legacy profile/application records.

`POST /internal/v1/auth-email/projection` accepts signed Auth success events containing `eventId`, `identityId`, canonical `email`, `emailVerified:true`, increasing `emailRevision`, and the original `verifiedAt`. Use the dedicated `CRAVES_EMAIL_PROJECTION_INTERNAL_KEY` (UTF-8, at least 32 bytes), shared only with Auth. The framing is HMAC-SHA256 of `POST\n/internal/v1/auth-email/projection\n<epoch seconds>\n<raw JSON>` with `X-Craves-Email-Timestamp` and hex `X-Craves-Email-Signature`; maximum skew 300 seconds and maximum body 4096 bytes. Duplicate JSON fields, unknown fields, trailing data, unverified events and invalid revisions are rejected. No public APIM product exposes this route.

An identity-scoped PostgreSQL transaction advisory lock serializes projection receipt/application with profile/application creation. The latest projection is retained even when neither profile nor chef row exists. Successful updates change the email projections without changing chef business approval. Duplicate events are idempotent, stale revisions cannot overwrite newer ones, and conflicting same-revision or event-ID content returns 409. Receipts are append-only, store keyed request fingerprints, and contain no raw request payload. Projection revisions must advance at the database boundary. Response `{status,emailRevision}` reports APPLIED, DUPLICATE or STALE with an acknowledged revision at least as new as the event.

Customer email remains optional. A nonempty legacy profile `email` parameter must match that authenticated identity's ACTIVE verified canonical Auth address; otherwise the service returns `EMAIL_VERIFICATION_REQUIRED` or a temporary authority-unavailable error. Omission preserves the existing canonical address and applies a retained projection when creating a later profile. A verified replacement remains controlled by Auth; arbitrary profile edits cannot establish verification.

Chef submission and approval each perform a fresh protected Auth identity email lookup and reject unverified, inactive, mismatched or unavailable authority responses. Submission uses the authenticated identity, never identity or verification claims from a browser payload. Approval re-reads the application under the same identity lock and rechecks PENDING status before granting the chef role. Existing document/business approval rules remain intact.

Required tests: `AuthEmailProjectionSecurityTest`, `AuthEmailProjectionDbTest`, and all existing User/Chef tests. The disposable database suite requires GitHub CI, explicit `EMAIL_TEST_DISPOSABLE=true`, dedicated localhost `craves_email_test`, and `EMAIL_TEST_DB_USER/PASSWORD`. It resets only `email_userchef_test`, uses existing PostGIS migrations, and tests clean/upgrade/replay, retained pre-profile events, duplicate/stale/conflicting updates, concurrent create/update, chef verification enforcement and wrong-role denial. CI must assert all DB cases ran with zero skips. Production Flyway validation remains read-only.
